# Стандарт формату індексу BDEA

**BDEA — Backup Data Extended Archive.** Формат довготривалого офлайн-архіву
для носіїв з високою стабільністю та одноразовим записом (оптичні диски типу
BD-R XL, стрічкові системи LTO тощо). Цей документ описує формат індексного
файлу `.bdea`. Він не визначає поведінку конкретних застосунків (див.
[§10](#10-нотатки-для-розробників)).

Це авторитетний опис формату. Канонічний розібраний приклад — у
[`samples/music.bdea`](samples/music.bdea).

Це переклад [`BDEA-1.0_STANDARD.md`](BDEA-1.0_STANDARD.md). У разі розбіжностей
англомовна версія має пріоритет.

## 1. Призначення та межі стандарту

Мета BDEA — дати змогу згодом відновити **бібліотеку** архівованих файлів у
повній логічній структурі, а не просто набір байтів, без залежності від
початкового комп'ютера, бази даних чи спеціального програмного забезпечення.
Стандарт стосується **виключно** формату індексного файлу `.bdea`: як текстом
описати структуру бібліотеки, томи, каталоги, файли та історію їх змін. Він
не регламентує фізичне розташування даних на носії, програмне забезпечення
для запису носіїв чи політику резервного копіювання.

## 2. Базові поняття

| Термін | Значення |
|---|---|
| **Archive (архів)** | Загальна структура BDEA: одна або кілька незалежних бібліотек. |
| **Library (бібліотека)** | Логічно ізольована колекція даних (наприклад, `Music`, `Documents`, `Photos`). Має власний простір каталогів, власний індекс `.bdea` і може бути відновлена незалежно від інших бібліотек. |
| **Volume (том)** | Один фізичний носій (наприклад, один диск чи стрічка), що належить бібліотеці. Бібліотека росте, додаючи томи з часом (`Music-001`, `Music-002`, ...). |

**Бібліотеки повністю ізольовані одна від одної.** Бібліотека ніколи не
посилається на іншу бібліотеку, дублікати між бібліотеками не виявляються, і
кожна бібліотека має власні правила та власний шлях відновлення. BDEA — це
набір автономних структур для кожної бібліотеки, а не єдиний монолітний
архів.

## 3. Модель ідентифікації файлів

Використовуються два окремі, свідомо розділені поняття «ідентичності»:

- **Фізична/позиційна ідентичність** — `(volume_id, file_id)`. Ідентифікує
  один *запис* архівованого файлу всередині бібліотеки: на якому томі його
  записано і його локальний ід в межах цього тому. `file_id` унікальний лише
  в межах свого `volume_id`.
- **Ідентичність вмісту** — `size` + `hash`. Ідентифікує *чим файл насправді
  є*, незалежно від його імені чи розташування. Два записи з однаковими
  `size`+`hash` — це один і той самий вміст, де б він не зустрічався.

Наслідки використання ідентичності вмісту замість імені файлу:

- Дублікати вмісту будь-де в бібліотеці можна виявити (порівнюючи
  `size`+`hash` серед усіх записів `F`, що вже є в індексі).
- Цілісність вмісту можна перевірити за записаним хешем.
- Файл може переміщатися між каталогами, або навіть бути доданим повторно під
  іншим іменем, не втрачаючи своєї ідентичності.

Ім'я ніколи не є авторитетним джерелом — це метадані, а не ідентичність.

## 4. Загальна структура файлу

**Іменування файлів.** Індексний файл бібліотеки повинен мати розширення
`.bdea`; решта імені файлу довільна — цей стандарт не вимагає, щоб вона
збігалася зі значенням `! LIBRARY`, повторювала його регістр чи якось інакше
кодувала, якій бібліотеці належить файл. Читач визначає це з декларації
заголовка `! LIBRARY` (§5) усередині файлу, а не з імені файлу. Один файл на
одну бібліотеку — файл однаково може називатися `music.bdea`,
`music-2026-08-23.bdea` чи як завгодно інакше, аби закінчувався на `.bdea`;
застосунок ніколи не повинен визначати бібліотеку з імені файлу.

Файл `.bdea` — це текст у UTF-8 з трьома видами рядків:

- **Декларації** — починаються з `!`, токени розділені пробілами:
  `! KEYWORD value...`. Це машинно-читані рядки.
- **Коментарі** — починаються з `#`, довільний текст, ігнорується парсерами.
- **Записи** — рядки даних формату `TAG|поле1|поле2|...`, розділені `|`.
  `TAG` — це те, що визначено декларацією `! RECORD` (§7) — один або кілька
  символів (`VOLUME_START`, `VOLUME_END`, `AF`, `XF`, `XD`, `RD`, `RF`,
  `D`, `F`, `S` у поточній схемі).

Порожні рядки допускаються як візуальні розділювачі (наприклад, між секціями
томів).

**Формат є самоописовим.** Порядок полів для кожного тегу запису не
зашитий жорстко в цьому стандарті — він оголошується прямо у файлі через
рядки `! RECORD` (§7), які мають з'явитися перед будь-яким рядком даних із
цим тегом. Коректний парсер спочатку читає декларації `! TYPE`/`! RECORD`, а
потім використовує це відображення для розбору наступних рядків даних.

**Індекс є доповнюваним (append-only) і накопичувальним.** Той самий файл
`.bdea` *доповнюється* щоразу, коли виробляється новий том, і оновлений файл
записується також і на цей новий том. Це означає:

- Копія індексу на кожному томі містить *усю історію бібліотеки до цього
  моменту* — а не лише вміст цього конкретного тому.
- Найновіший том, який у вас є, завжди містить найповніший/найактуальніший
  індекс усієї бібліотеки (наслідки цього для носіїв одноразового запису —
  див. §8).
- В принципі бібліотеку можна повністю переглянути з копії індексу лише
  одного тому, навіть без наявності решти фізичних томів — ця копія
  вкаже, на якому томі фізично лежать байти будь-якого конкретного файлу.

## 5. Заголовкові декларації

З'являються один раз, на початку файлу — до відкриття першої секції тому
(`VOLUME_START`, §7).

| Декларація | Приклад | Значення |
|---|---|---|
| `! TEXT_ENCODING` | `utf-8` | Кодування самого файлу `.bdea`. |
| `! TEXT_NORMALIZATION` | `NFC` | Форма нормалізації Unicode для тексту файлу. |
| `! ARCHIVE_TYPE` | `BDEA` | Ідентифікатор формату. |
| `! VERSION` | `1.0` | Версія формату (див. §11). |
| `! LIBRARY` | `Music` | Назва цієї бібліотеки. |
| `! NAME_ENCODING` | `utf-8` | Кодування, що використовується для полів `dir_name`/`file_name`. |
| `! NAME_NORMALIZATION` | `NFC` | Нормалізація Unicode, застосована до імен. |
| `! NAME_FORBIDDEN_CHARACTERS` | `/ \ : * ? " < > \|` | Символи, яких не повинно бути в іменах (надмножина зарезервованих символів Windows/exFAT — безпечний вибір для носія, який мають читати з будь-якої файлової системи). |
| `! CONTENT_HASH_ALGORITHM` | `md5` | Алгоритм хешування, що ідентифікує вміст файлу. |
| `! CONTENT_HASH_ENCODING` | `base32` | Кодування, у якому хеш подано текстом. |
| `! CONTENT_HASH_SCOPE` | `file-content` | Що саме хешується (сирі байти файлу, а не, наприклад, ім'я+вміст). |

Це канонічна, чинна форма заголовка — саме таким має бути заголовок нових
файлів `.bdea`.

## 6. Система типів (`! TYPE`)

Оголошує примітивний тип кожного поля, що використовується в записах, аби
файл був самоописовим і придатним для незалежного розбору.

| Назва типу | Вид | Примітки |
|---|---|---|
| `dir_id` | `uint32` | Глобальний для всієї бібліотеки — призначається один раз на каталог і ніколи не використовується повторно, незалежно від того, який том його ввів. `0` завжди позначає корінь бібліотеки, який не має власного запису `D` (бо в нього немає ні імені, ні батька); кожен реальний каталог нумерується від `1` і далі, у порядку введення (§7 `D`, `F`, `S`). |
| `last_dir_id` | `uint32` | Той самий вид, що й `dir_id`; найбільший `dir_id`, призначений у бібліотеці станом на цей том (§7 `VOLUME_END`). |
| `new_dir_id` | `uint32` | Той самий вид, що й `dir_id`; виправлений каталог, під який виправлення `RF` переносить запис (§7 `RF`). |
| `parent_dir_id` | `uint32` | `0` = корінь простору імен бібліотеки. |
| `new_parent_dir_id` | `uint32` | Той самий вид, що й `parent_dir_id`; виправлений батьківський каталог, який виправлення `RD` надає каталогу (§7 `RD`). |
| `file_id` | `uint64` | Локальний для тому. |
| `target_file_id` | `uint64` | Той самий вид, що й `file_id`; запис `F`, на який посилається псевдонім `S` (§7 `S`). |
| `size` | `uint64` | Байти. |
| `dir_name` | `string max=120` | Ім'я каталогу. |
| `file_name` | `string max=120` | Ім'я файлу; використовується також псевдонімами `S`, які займають власну позицію у файловому дереві (§7 `S`). |
| `new_dir_name` | `string max=120` | Той самий вид, що й `dir_name`; виправлене ім'я, яке виправлення `RD` надає каталогу (§7 `RD`). |
| `new_file_name` | `string max=120` | Той самий вид, що й `file_name`; виправлене ім'я, яке виправлення `RF` надає файлу чи псевдоніму (§7 `RF`). |
| `hash` | `string max=32` | Закодований хеш вмісту (26 символів для base32 MD5; додатковий запас довжини дозволяє довший хеш, якщо `CONTENT_HASH_ALGORITHM` колись зміниться). |
| `extra` | `string max=256` | Довільне поле в записах `D`/`F` (§7 `D`, §7 `F`), наприклад для тегів. Залишається порожнім, якщо застосунок його не використовує. |
| `volume_id` | `uint32` | Локальний для бібліотеки. |
| `target_volume_id` | `uint32` | Той самий вид, що й `volume_id`; том запису `F`, на який посилається псевдонім `S` (§7 `S`). |
| `volume_label` | `string max=120` | Людська/фізична позначка, надрукована на носії. |
| `date_time` | `string max=15` | `YYYY-MM-DD_hhmm` — завжди час, коли *застосунок-виробник* згенерував записи індексу навколо, а не власний час запису фізичного носія (поза межами стандарту, §1). Формування індексних записів одного тому вважається єдиним швидким кроком, тож кожне поле `date_time` у межах секції цього тому (`VOLUME_START`, `VOLUME_END`, будь-які `AF`/`XF`/`XD`/`RD`/`RF`) традиційно несе *те саме* значення — це не пара «початок/кінець» тривалості фізичного запису. Обов'язкове в `VOLUME_START`/`VOLUME_END`; необов'язкове, але бажане в `AF`/`XF`/`XD`/`RD`/`RF` (преамбула §7) — бажане тому, що ці позначки часу допомагають відновити історію змін конкретного файлу чи каталогу, необов'язкове тому, що ту саму дату й так можна визначити з тому, у якому міститься запис. |
| `total_vol_files` | `uint64` | Кількість записів `F`, фізично записаних у власній секції даного тому (§7 `VOLUME_END`). |
| `vol_files_size` | `uint64` | Той самий вид, що й `size`; сума `size` по записах `F` саме цього тому — розмірний відповідник `volume_hash` нижче (§7 `VOLUME_END`). |
| `volume_hash` | `string max=32` | Та сама форма, що й у `hash` (§6 `hash`); контрольна сума за один том, обчислена з інших хешів, що вже є в індексі, а не з вмісту якогось файлу (§7 `VOLUME_END`). |
| `file_key` | `volume_id file_id` | Композитний тип: повна фізична ідентичність запису файлу (§3). |

`file_key` — це композитний тип на рівні документації: він називає поняття
«кортеж, що однозначно локалізує цей запис»; декларації `! RECORD` для
`AF`/`XF`/`RF` усе одно перелічують `volume_id`/`file_id` як окремі поля, а
не посилаються на цю композитну назву напряму. У каталогів немає
аналогічного композитного типу: `dir_id` сам по собі вже є повною
ідентичністю каталогу, оскільки він глобальний для всієї бібліотеки.

## 7. Схема записів (`! RECORD`)

Десять тегів записів діляться на два види. П'ять — це **виправлення** —
`AF`, `XF`, `XD`, `RD`, `RF` — вони не вводять нічого нового, а діють на
запис, який уже написав один із інших п'яти, позначаючи його канонічним,
зниклим чи перейменованим/переміщеним. Ті інші п'ять вводять **нові дані**,
яких у бібліотеці ще не було, — `VOLUME_START`/`VOLUME_END`, `D`, `F`, `S` —
нову секцію тому, каталог, файл чи псевдонім.

Ім'я поля, що закінчується на `?` у декларації `! RECORD`, позначає його як
**необов'язкове й кінцеве**: рядок даних із цим тегом може його не містити —
матиме на одне поле, розділене `|`, менше, ніж оголошено. Станом на
`! VERSION 1.0` це стосується `extra?` у `D` та `F` (нижче), а також
`date_time?` в `AF`/`XF`/`XD`/`RD`/`RF` (нижче) — усі інші поля обов'язкові.
Коректний парсер має приймати рядок як із кінцевим необов'язковим полем, так
і без нього, трактуючи відсутнє поле як порожнє/відсутнє. Саме це дозволяє
додати `extra` до рядка пізніше (наприклад, щоб прикріпити теги), або не
вказувати `date_time` у виправленні, чию дату й так можна визначити з тому,
в якому воно міститься (§6 `date_time`), не роблячи невалідними старіші
рядки, що існували до цього поля, і без потреби переписувати кожен наявний
рядок.

### `VOLUME_START` / `VOLUME_END` — межа тому

```
! RECORD VOLUME_START volume_id volume_label date_time
! RECORD VOLUME_END volume_id volume_label date_time total_vol_files vol_files_size volume_hash last_dir_id
```

`VOLUME_START` оголошує один том (один фізичний носій) і відкриває його
секцію; `VOLUME_END` закриває її. Кожен запис `AF`, `XF`, `XD`, `RD`, `RF`,
`D`, `F` та `S` між `VOLUME_START` і відповідним йому `VOLUME_END` було
записано під час виробництва саме цього тому — спочатку виправлення, потім
нові дані (§8):

- Записи `AF`/`XF`/`RF` можуть з'являтися тут, хоча вони можуть посилатися
  на файл на **будь-якому** томі (§7 `AF`, `XF`, `RF`) — для них важливе
  саме їхнє явне поле `volume_id`, а не позиція у файлі. Записи `XD`/`RD`
  так само можуть посилатися на `dir_id`, призначений будь-яким попереднім
  томом (§7 `XD`, `RD`) — каталогам `volume_id` взагалі не потрібен,
  оскільки `dir_id` вже глобальний (§3, §10).
- Записи `D` у цьому діапазоні оголошують каталоги, які цей том вводить
  вперше (§7 `D`) — каталог, що вже існує в бібліотеці, не повторюється.
- Записи `F` у цьому діапазоні отримують свій `volume_id` саме з цієї секції
  (§7 `F`) — це єдине місце, де фіксується том файлу.
- Записи `S` у цьому діапазоні отримують свій `volume_id` так само, як і
  `F` (§7 `S`) — хоча *вміст*, на який вони посилаються, може бути на
  будь-якому томі, через власне явне поле `target_volume_id`.

Поля, спільні для обох записів:

- `volume_id` — внутрішній числовий ід тому в межах бібліотеки; повторюється
  в `VOLUME_END`, аби читач (або людина, що переглядає файл) міг
  переконатися, яку саме секцію закрито, і аби можна було виявити обірвану
  чи пошкоджену секцію (`VOLUME_START` без відповідного `VOLUME_END`).
- `volume_label` — позначка, написана/надрукована на фізичному носії;
  повторюється в `VOLUME_END` з тієї самої причини, що й `volume_id` —
  якщо значення на двох кінцях секції розійдуться, це ознака проблеми.
- `date_time` — коли застосунок-виробник згенерував індексні записи цього
  тому (§6 `date_time`). Формування секції одного тому вважається єдиним
  швидким кроком — окремим від фізичного запису і зазвичай значно
  коротшим за нього — тож це значення однакове на `VOLUME_START`,
  `VOLUME_END` і будь-яких записах `AF`/`XF`/`XD`/`RD`/`RF` у тій самій
  секції; це не пара «початок/кінець» тривалості фізичного запису.

Поля, властиві лише `VOLUME_END` — усе, що фізично додав цей том сам, плюс
`last_dir_id` як єдине значення для всієї бібліотеки, достатньо дешеве, щоб
тримати його без розв'язання жодного виправлення (§10):

- `total_vol_files` — кількість записів `F`, фізично записаних у власній
  секції цього тому. Записи `S` (§7 `S`) сюди ніколи не входять — псевдонім
  додає нове ім'я, а не новий вміст.
- `vol_files_size` — сума `size` по тих самих записах `F`: власний фізичний
  обсяг байтів цього тому, розмірний відповідник `volume_hash` нижче.
- `volume_hash` — контрольна сума саме власних записів `F` цього тому,
  отримана виключно з їхніх значень `hash`, уже записаних кількома рядками
  вище в цій самій секції (§6 `hash`) — ніколи через повторне читання
  справжнього вмісту якогось файлу. Обчислюється так: конкатенувати, у
  порядку появи в секції цього тому, поле `hash` кожного запису `F` — без
  роздільника між ними, оскільки кожен `hash` у межах одного файлу має
  однакову фіксовану довжину (§6 `hash`), поки не змінюються
  `! CONTENT_HASH_ALGORITHM`/`! CONTENT_HASH_ENCODING`, що й робить пряму
  конкатенацію однозначною — потім застосувати `! CONTENT_HASH_ALGORITHM`
  до отриманих байтів і закодувати результат за допомогою
  `! CONTENT_HASH_ENCODING` (§5) — ті самі дві заголовкові декларації, що
  вже використовуються для кожного хешу файлу, лише застосовані до іншого
  входу. Записи `S` нічого не додають до цього, бо не мають власного
  `hash` (§7 `S`); том, який раптом не додає жодного запису `F`, використовує
  хеш порожнього входу.
- `last_dir_id` — найбільший `dir_id`, призначений у бібліотеці станом на
  цей том; простий монотонний максимум, не залежний від
  `AF`/`XF`/`XD`/`RD`/`RF` (§7 `D`) — єдине значення для всієї бібліотеки,
  яке `VOLUME_END` усе ж таки несе, оскільки для нього не потрібно
  розв'язувати жодну історію виправлень.

`total_vol_files`/`vol_files_size` — єдині потомні підсумки, які зберігає
`! VERSION 1.0` — додавання `S`, і кожне з виправлень (`AF`, `XF`, `XD`,
`RD`, `RF`), не мають власного окремого лічильника. Жодне з цих двох полів
нічого не каже про *активну* кількість файлів чи обсяг байтів бібліотеки
після врахування пізніших виправлень (§10) — читач, якому потрібне саме це,
розв'язує весь накопичувальний журнал повністю, так само, як він розв'язує
будь-що інше в активному поданні; читач, якому потрібно знати, скільки
виправлень містить секція певного тому, просто рахує рядки
`AF`/`XF`/`XD`/`RD`/`RF` у цій секції, так само, як рахував би будь-що інше
у файлі.

```
VOLUME_START|2|Music-002|2026-08-14_1111
AF|1|4|2026-08-14_1111
XF|1|7|2026-08-14_1111
...
VOLUME_END|2|Music-002|2026-08-14_1111|6|41474037|BV6N47NFZD6XHIFB2EH2HR625I|5
```

### `D` — Каталог

```
! RECORD D dir_id parent_dir_id dir_name extra?
```

Логічний каталог у дереві простору імен бібліотеки.

- `dir_id` — глобальний для всієї бібліотеки: призначається один раз, коли
  том вперше вводить цей каталог, і ніколи не переприсвоюється пізнішим
  томом — навіть тим, що додає до нього ще файли. `0` завжди позначає
  корінь бібліотеки — у нього немає ні власного імені, ні батька, тож йому
  не потрібен запис `D`; кожен реальний каталог нумерується від `1` і далі,
  у порядку введення, будь-де, де на нього посилається поле виду `dir_id`
  (`parent_dir_id` нижче, а також власне поле `dir_id` у `F`/`S`, §7 `F`,
  §7 `S`).
- `parent_dir_id` — `dir_id` батьківського каталогу (`0` = корінь). Оскільки
  `dir_id` глобальний, батьківський каталог міг бути оголошений і раніше,
  не обов'язково поточним томом.
- `dir_name` — ім'я каталогу.
- `extra?` — необов'язкове, кінцеве поле (преамбула §7); довільне (§6
  `extra`), наприклад для тегів. Порожнє або відсутнє, якщо застосунок його
  не заповнює.

Каталоги формують єдине, стабільне, доповнюване (append-only) дерево
простору імен для всієї бібліотеки (а не по одному дереву на том). Порожні
каталоги можна не вказувати. Оскільки `dir_id` глобальний, конкретна
логічна папка (наприклад, `Band - Album`)
оголошується рівно один раз — тим томом, що вводить її вперше; пізніший
том, що додає файли до вже наявної папки, не переоголошує її, а просто
посилається на вже наявний `dir_id` у своїх записах `F` (див. розібраний
приклад, §9).

**Пара `(parent_dir_id, dir_name)` унікальна назавжди.** Дві директорії
можуть мати однакове `dir_name` (з різними батьками) або однаковий
`parent_dir_id` (з різними іменами), але ніколи обидві властивості
одночасно — жодні дві директорії не можуть одночасно мати той самий
`parent_dir_id` і те саме `dir_name`. Це діє протягом усієї історії
каталогу, а не лише для його активного вмісту: навіть каталог, чиє
піддерево вже позначено зниклим через `XD`, і далі займає свою пару
`(parent_dir_id, dir_name)`, бо `XD` не видаляє сам каталог (§7 `XD`). Тому
продовження чи відновлення *тієї самої* логічної папки повторно використовує
її наявний `dir_id`, а не заводить новий під тим самим іменем і батьком
(див. відновлення `Sandra Bernardo`, §9 п.6); справді нову директорію, що
інакше зіткнулась би з наявним іменем, вирішують через `RD` (див. розділення
`(flac)`/`(mp3)`, §9 п.5).

```
D|1|0|Band
D|2|1|Band - Album
```

### `F` — Файл

```
! RECORD F file_id dir_id file_name size hash extra?
```

Запис архівованого файлу. **`volume_id` не є полем `F`.** Том файлу —
позиційний, а не поле самого запису: запис `F` належить тому тому, у секції
`VOLUME_START`...`VOLUME_END` якого він фізично знаходиться (§7
`VOLUME_START`/`VOLUME_END`) — читач відстежує «поточний том» під час
послідовного сканування і проставляє його кожному зустріченому рядку `F`.

Це свідомий вибір заради економії місця: реальні бібліотеки міститимуть
значно більше файлів, ніж томів, тож повторювати `volume_id` в кожному
записі `F` було б марнотратно, тоді як відстежувати його один раз на секцію
для читача нічого не коштує. Каталог файлу, натомість, не позиційний:
`dir_id` — глобальний для всієї бібліотеки (§7 `D`), тож читач розв'язує
його відносно єдиного, спільного для всієї бібліотеки дерева каталогів,
побудованого з усіх побачених досі записів `D`, незалежно від того, який
том оголосив цей каталог.

- `file_id` — унікальний лише в межах `volume_id` (повна фізична
  ідентичність — `(volume_id, file_id)`, тобто `file_key`); сам `volume_id`
  береться з секції тому, що охоплює цей запис, а не з самого запису.
- `dir_id` — глобальний ід каталогу, що містить файл (§7 `D`); `0` означає,
  що файл лежить прямо в корені бібліотеки — той самий сентінел, що й у
  `parent_dir_id` (§7 `D`) — корінь не має власного запису `D`, на який
  можна було би послатися.
- `file_name` — ім'я файлу (не ідентичність, див. §3).
- `size`, `hash` — ідентичність вмісту (§3); використовуються для виявлення
  дублікатів, що вже є будь-де в бібліотеці, та для перевірки цілісності.
- `extra?` — необов'язкове, кінцеве поле (преамбула §7); довільне (§6
  `extra`), наприклад для тегів. Порожнє або відсутнє, якщо застосунок його
  не заповнює.

```
F|1|2|cover.jpg|125142|P625I35ZX7YR6Y4NILBDDE3MQP
F|2|2|...01 Baroque Harpsichord and Strings.flac|11124049|55HH6H7GAWRZZVD7FIC7LD5O4X|baroque,epic
```

### `S` — Симлінк

```
! RECORD S file_id dir_id file_name target_volume_id target_file_id
```

Псевдонім: нова позиція в дереві, яка сягає вмісту, що вже тримає десь
інший запис `F`, замість архівування ще однієї фізичної копії. `S` існує
для бібліотек, які намагаються уникати зберігання дублікатів одного й того
самого вмісту (див. `AF` нижче): без нього зробити той самий вміст
доступним більш ніж з одного місця в дереві (наприклад, той самий
`cover.jpg` у двох різних папках альбомів) можна було б лише повторно
записавши ці байти на том — або взагалі не мати цього другого місця.

- `file_id` — власний локальний ід цього псевдоніма, узятий з *того самого*
  лічильника за томом, що й `file_id` у `F`, а не з окремого простору
  нумерації — тож `(volume_id, file_id)`, де `volume_id` визначається
  позиційно так само, як у `F` (§7 `VOLUME_START`/`VOLUME_END`), однаково
  адресує і `F`, і `S`. Саме це дозволяє `XF`/`RF` виправляти псевдонім так
  само, як вони виправляють файл (§7 `XF`, §7 `RF`).
- `dir_id` — де саме в дереві бібліотеки живе цей псевдонім (глобальний,
  точно як `dir_id` у `F`, включно з `0` як позначенням кореня, §7 `D`, §7
  `F`). `AF`/`XF` адресують наявний запис виключно за `file_key` і взагалі
  не потребують `dir_id`; `S` — інакше, оскільки він створює цілком нову
  позицію в дереві, тож йому потрібне це поле, щоб вказати, де саме ця
  позиція перебуває.
- `file_name` — власне ім'я цього псевдоніма в цій позиції; незалежне від
  власного `file_name` цілі (§7 `F`) — псевдонім може мати те саме ім'я, що
  й ціль, або зовсім інше.
- `target_volume_id`, `target_file_id` — наявний запис `F`, чийого вмісту
  сягає цей псевдонім (може бути на будь-якому томі, той самий шаблон, що
  й у `AF`/`XF`, §3 `file_key`).

`S` не несе власних `size`/`hash` — вміст, якого він сягає, вже врахований
через `F`-запис своєї цілі, тож псевдонім додає дереву нове ім'я, не
додаючи нових байтів чи нового врахованого вмісту (§7 `VOLUME_END`, §10).

**Розв'язання цілі через `AF`/`XF`/`XD`.** Поле цілі псевдоніма визначає
*який саме вміст* він сягає, а не назавжди зафіксований фізичний запис:
читач розв'язує його так само, як будь-який інший вміст у бібліотеці —
через історію `AF`/`XF`/`XD`, застосовну до цього вмісту (§10 «Розв'язання
активного подання»). Конкретно: якщо цільовий запис пізніше заміщено через
`AF` (натомість канонічною названо справжню другу фізичну копію цього
вмісту — див. нижче), псевдонім прозоро переходить на новий канонічний
запис; якщо цільовий запис пізніше позначено `XF` (або каталог, що його
містить, видалено через `XD`) і ніде більше в бібліотеці не лишилось іншої
копії цього вмісту, псевдонім стає «висячим» — так само, якби вміст просто
зник. Виправлення `RF`/`RD` щодо власного імені/розташування цілі жодним
чином не впливають на псевдонім — він адресує ціль за `file_key`, а не за
`file_name`, тож ціль можна вільно перейменовувати чи переносити без жодного
впливу на все, що на неї посилається як псевдонім.

```
S|1|6|cover.jpg|1|1
```

(Із секції `Music-003` у `samples/music.bdea` — цей псевдонім сягає
`F|1|2|cover.jpg` із другої позиції в дереві, `dir_id=6`, обкладинки в
mp3-папці, замість повторного архівування цих байтів; див. §9.)

### `AF` — Активний файл

```
! RECORD AF volume_id file_id date_time?
```

Оголошує, що `(volume_id, file_id)` — канонічний/пріоритетний фізичний
запис, який слід використовувати для цього вмісту надалі. Як і `S` (§7
`S`), `AF` існує для бібліотек, які намагаються уникати дублікатів
фізичних копій одного й того самого вмісту: без нього повторне
архівування файлу, чий вміст уже є в бібліотеці, просто лишало б дві
незалежні, однаково «активні» копії. Завдяки `AF` архіваріус визначає,
яка фізична копія є актуальною; симлінк на неї, якщо він потрібен в
іншому місці дерева, тоді робиться через `S`. Обидва механізми, `AF` і
`S`, необов'язкові — бібліотека, якій дедублікація не важлива, може
взагалі не використовувати жодного з них.

На відміну від `D`/`F`/`S`, `AF` може вказувати на файл на **будь-якому**
томі (не лише на поточному). Типове застосування: той самий вміст
архівується більше одного разу — можливо, на кількох різних томах (збіг
`size`+`hash`, наприклад той самий файл, доданий пізніше повторно на
іншому томі, див. §9) — `AF` називає рівно один із цих записів «тим самим»
файлом для показу/використання надалі. Це **не** вимагає позначати решту
заміщених записів як `XF` — вони можуть лишатися цілком валідними,
читабельними архівними копіями; просто більше не є тими, на які вказують
як на канонічні. Скільки б копій цього вмісту не існувало по всьому
архіву, після того як `AF` назве одну з них, в активному поданні
бібліотеки лишається рахуватися рівно одна — решта випадають з цього
підрахунку без потреби в `XF`.

- `volume_id`, `file_id` — запис, який оголошується канонічним (§3
  `file_key`). Завжди запис `F`, ніколи `S` (§7 `S`) — псевдонім не тримає
  власного вмісту, тож ніколи не може бути *тією* канонічною фізичною
  копією чогось; «канонічний для вмісту» має сенс лише серед записів, що
  справді тримають байти.
- `date_time?` — необов'язкове, але бажане (§6 `date_time`): коли це
  виправлення було дописано до індексу — не властивість жодної з фізичних
  копій. Якщо вказане, збігається з позначкою часу `VOLUME_START`/
  `VOLUME_END` тому, до якого належить; якщо не вказане, читач бере саме
  цю позначку часу тому, оскільки дата виправлення й так завжди збігається
  з датою тому, що його містить.

```
AF|1|4|2026-08-14_1111
```

(Із секції `Music-002` у `samples/music.bdea` — з двох тепер відомих копій
того самого вмісту, `F|4|2` з `Music-001` і власного `F|6|2` з `Music-002`,
це оголошує оригінал з `Music-001` (`volume=1, file=4`) канонічним надалі;
див. §9.)

### `XF` — Видалити файл

```
! RECORD XF volume_id file_id date_time?
```

Оголошує, що запис за адресою `(volume_id, file_id)` слід пропускати при
подальшому відновленні бібліотеки, починаючи з цього моменту. Як і `AF`,
може посилатися на запис будь-якого тому. Що саме означає «зниклий»,
залежить від типу запису:

- Для запису `F`: фізична копія стала недоступною — нечитабельною,
  пошкодженою чи втраченою саме на цьому носії. Якщо десь у бібліотеці
  немає іншого, неушкодженого запису `F` з таким самим `size`+`hash`, цей
  вміст фактично втрачено.
- Для запису `S` (§7 `S`): видалено сам псевдонім — з вмістом, на який він
  посилався, нічого не сталося, він просто перестає бути досяжним із цієї
  однієї позиції в дереві.

- `volume_id`, `file_id` — запис, який позначають як зниклий (§3
  `file_key`).
- `date_time?` — необов'язкове, але бажане (§6 `date_time`): коли це
  виправлення було дописано до індексу — не момент, коли носій справді
  вийшов з ладу чи коли це було помічено. Якщо вказане, збігається з
  позначкою часу `VOLUME_START`/`VOLUME_END` тому, до якого належить; якщо
  не вказане, читач бере саме цю позначку часу тому.

```
XF|1|7|2026-08-14_1111
```

(Із секції `Music-002` у `samples/music.bdea` — `F|7|2` з `Music-001`
(`Vivaldi - Concerto No. 1 in G minor, RV 324.flac`) став нечитабельним на
цьому диску; більше ніщо в бібліотеці не має такого самого хешу, тож цей
вміст втрачено, якщо його не відновлять пізніше; див. §9.)

### `XD` — Видалити каталог

```
! RECORD XD dir_id date_time?
```

Скорочення для `XF`: одразу оголошує зниклим кожен запис `F`/`S`, поданий
будь-де під `dir_id` — включно з будь-яким каталогом-нащадком, незалежно
від того, на якому томі (томах) їх записано — замість написання окремого
`XF` для кожного файлу. `XD` існує виключно заради цієї зручності й не
несе жодної іншої мети: якби його не існувало, позначення кожного з цих
записів через `XF` окремо дало б рівно те саме активне подання. Пишеться,
коли ціла гілка зникає одразу — наприклад, частина пошкодженого тому, що
вціліла і лишилась читабельною, не містила цю гілку.

- `dir_id` — каталог, чиє піддерево позначається як зниклий таким чином
  (§7 `D`). Оскільки `dir_id` ніколи не використовується повторно (§7
  `D`), самого лише цього поля достатньо, щоб ідентифікувати ціль — на
  відміну від `XF`, якому потрібне супутнє поле `volume_id` поряд із
  `file_id`, тут жодне супутнє поле не потрібне.
- `date_time?` — необов'язкове, але бажане (§6 `date_time`): коли це
  виправлення було дописано до індексу. Якщо вказане, збігається з
  позначкою часу `VOLUME_START`/`VOLUME_END` тому, до якого належить, так
  само як і в `XF`; якщо не вказане, читач бере саме цю позначку часу
  тому.

`XD` не видаляє сам каталог — `dir_id` лишається постійним логічним шляхом
у дереві (§7 `D`), і його власний запис `D` (як і будь-які записи `D`
нащадків) лишається оголошеним так само, як і був. `XD` видаляє саме
вміст: кожен запис `F`/`S`, поданий під `dir_id` на момент цього
виправлення. Пізніший том усе ще може подавати нові записи `F`/`D` під тим
самим `dir_id`, так само як міг би й до `XD` — каталог і далі існує як
шлях; зникає лише те, що було в ньому подано на момент виправлення.

**Порядок у межах однієї секції.** Оскільки пара `(parent_dir_id, dir_name)`
лишається назавжди закріпленою за каталогом навіть після `XD` (§7 `D`),
відновлення тієї самої логічної папки — наприклад, одразу після того, як
том із її попередніми копіями вийшов з ладу — повторно використовує наявний
`dir_id` цього каталогу, а не заводить новий. Якщо один і той самий том
одночасно й виводить `dir_id` з ужитку через `XD`, і подає під ним нові
записи `F`/`D`, `XD` має стояти в секції **перед** цими новими записами:
читач обробляє журнал по порядку (§10), і `XD` гасить усе, що подано під
`dir_id` саме на своїй позиції в журналі, — записи, розміщені раніше за
нього, той самий `XD` і погасить (див. відновлення `Sandra Bernardo` в
`Music-004`, §9 п.6).

Як і `XF`, це твердження про активне подання індексу, а не твердження про
фізичний стан носія — формат не розрізняє справді невідновну копію від
такої, яку архіваріус просто вирішив вважати зниклою.

```
XD|4|2026-08-24_1000
```

(Із секції `Music-004` у `samples/music.bdea` — фізичний диск `Music-002`
виявився повністю несправним, тож `dir_id=4` (Sandra Bernardo) і п'ять
записів `F`, подані під ним, одночасно вилучаються з активного подання
замість написання окремого `XF` для кожного файлу; див. §9.)

### `RD` — Перейменувати/Перемістити каталог

```
! RECORD RD dir_id new_parent_dir_id new_dir_name date_time?
```

Виправляє `parent_dir_id` і/або `dir_name` наявного каталогу (§7 `D`) надалі,
без написання жодного нового запису `D`, `F` чи `S`, і без будь-якого
впливу на архівовані байти. Оскільки дерево будується зі зв'язків
`dir_id`/`parent_dir_id`, а не з імен (§7 `D`), один `RD` одразу переносить
чи перейменовує все піддерево під `dir_id` — кожен файл і підкаталог під
ним і далі посилається на той самий `dir_id`, тож жоден з них не потребує
окремого виправлення.

- `dir_id` — каталог, що виправляється. Незмінний: `dir_id` — це постійна
  ідентичність каталогу (§7 `D`); змінюється лише його позиція/назва в
  дереві.
- `new_parent_dir_id` — виправлений батьківський каталог (§6
  `new_parent_dir_id`); якщо це виправлення — чисте перейменування,
  повторює наявний `parent_dir_id` без змін.
- `new_dir_name` — виправлене ім'я (§6 `new_dir_name`); якщо це виправлення
  — чисте переміщення, повторює наявне `dir_name` без змін.
- `date_time?` — необов'язкове, але бажане (§6 `date_time`): коли це
  виправлення було дописано до індексу. Якщо вказане, збігається з
  позначкою часу `VOLUME_START`/`VOLUME_END` тому, до якого належить, так
  само як і в `XF`; якщо не вказане, читач бере саме цю позначку часу
  тому.

Якщо з часом кілька записів `RD` стосуються того самого `dir_id`, перемагає
той, що з'являється в накопичувальному журналі останнім — читач завжди
визначає поточні `parent_dir_id`/`dir_name` каталогу за найновішим `RD`, що
його називає, або за його первісним записом `D`, якщо такого `RD` немає
(§10).

```
RD|2|1|Rafael Krux - The Epic Baroque Album (flac)|2026-08-20_0900
```

(Із секції `Music-003` у `samples/music.bdea` — трохи нижче в цій самій
секції під `Rafael Krux` (`dir_id=1`) ось-ось з'явиться нова сусідня папка,
`D|6|1|Rafael Krux - The Epic Baroque Album (mp3)`, тож цей `RD` заздалегідь
перейменовує наявну flac-папку, `dir_id=2`, додаючи суфікс `(flac)` —
батько лишається `1`, змінюється лише `dir_name`, оскільки обом папкам скоро
знадобляться розрізнювані назви. Кожен запис `F`/`S`, уже поданий під `2`,
переноситься разом з нею без жодного власного виправлення; див. §9.)

### `RF` — Перейменувати/Перемістити файл

```
! RECORD RF volume_id file_id new_dir_id new_file_name date_time?
```

Виправляє `dir_id` і/або `file_name` наявного запису `F` чи `S` надалі, без
повторного запису його вмісту. Це механізм для чистої помилки в назві чи
розміщенні: `size`+`hash` запису (для `F`) чи його ціль (для `S`) ніколи не
змінюються — лише те, де він лежить у дереві і як там називається.

- `volume_id`, `file_id` — запис, що виправляється (§3 `file_key`);
  адресує як `F`, так і `S`, так само як `AF`/`XF` (§7 `S`).
- `new_dir_id` — виправлений каталог (§6 `new_dir_id`); якщо це виправлення
  — чисте перейменування, повторює наявний `dir_id` без змін.
- `new_file_name` — виправлене ім'я (§6 `new_file_name`); якщо це
  виправлення — чисте переміщення, повторює наявне `file_name` без змін.
- `date_time?` — необов'язкове, але бажане (§6 `date_time`): коли це
  виправлення було дописано до індексу. Якщо вказане, збігається з
  позначкою часу `VOLUME_START`/`VOLUME_END` тому, до якого належить, так
  само як і в `XF`; якщо не вказане, читач бере саме цю позначку часу
  тому.

Якщо з часом кілька записів `RF` стосуються того самого `(volume_id,
file_id)`, перемагає найновіший — так само, як для `dir_id` розв'язується
`RD` (§10). `RF` не пов'язаний з `AF`: `AF` обирає, яка з кількох
незалежних фізичних копій *того самого вмісту* є канонічною; `RF` виправляє,
де в дереві лежить *один конкретний* запис, незалежно від того, чи існує
його дублікат.

```
RF|1|3|2|Rafael Krux - The Epic Baroque Album - 02 Classical Violin Concerto.flac|2026-08-20_0900
```

(Із секції `Music-003` у `samples/music.bdea` — виправляє помилку в назві
`F|3|2` з `Music-001`, прибираючи зайве слово «label» з `...02 Classical
Violin Concerto label.flac`; `dir_id` лишається `2`, змінюється лише
`file_name`. Чисте виправлення назви, без жодного дубліката; див. §9.)

`AF`, `XF`, `XD`, `RD` та `RF` — незалежні механізми: конкретне виправлення
може використовувати будь-яку їх комбінацію, але жоден із них не означає
інший автоматично. Разом вони — те, як BDEA підтримує виправлення без
перезапису носіїв одноразового запису: старий запис лишається фізично на
місці; `AF` перенаправляє, яка копія вважається канонічною, `XF`/`XD`
позначають копію (чи цілу гілку) як зниклу, а `RD`/`RF` виправляють
помилку в назві чи розміщенні на місці.

Усі п'ять — ручні виправлення, які видає архіваріус; ніщо у форматі не пише
їх автоматично. `AF`/`S`/`XF` — це відповіді на справжній збіг
`size`+`hash`, який виявляє застосунок (§10): назвати одну копію
канонічною, якщо обидві лишаються заархівованими (записати `AF`), додати
псевдонім замість повторного запису байтів, якщо вміст свідомо повинен
бути в кількох місцях (записати `S`, §7 `S`), зафіксувати, що копія
зіпсувалася (записати `XF`, або `XD`, якщо з нею зник цілий каталог), або
просто лишити два незалежні файли, що мають спільний вміст, як є. Чиста
помилка в назві чи розміщенні — без жодного справжнього дубліката —
натомість виправляється через `RD`/`RF`, що не потребує нових байтів і не
має нічого спільного з виявленням дублікатів.

## 8. Секції томів і зростання з часом

Тіло файлу — це послідовність секцій томів у порядку їх вироблення:

```
VOLUME_START|1|Music-001|2026-08-13_1232

D|1|0|Rafael Krux
D|2|1|Rafael Krux - The Epic Baroque Album
...
F|1|2|cover.jpg|125142|...

VOLUME_END|1|Music-001|2026-08-13_1232|8|82235912|QE4TTLSX56ECJLO3JQMQW74ECQ|3

VOLUME_START|2|Music-002|2026-08-14_1111

AF|1|4|2026-08-14_1111
XF|1|7|2026-08-14_1111

D|4|0|Sandra Bernardo
...
F|1|5|...

VOLUME_END|2|Music-002|2026-08-14_1111|6|41474037|BV6N47NFZD6XHIFB2EH2HR625I|5
```

Кожен новий том дописує: один рядок `VOLUME_START`, за потреби виправлення
`AF`/`XF`/`XD`/`RD`/`RF` (які можуть посилатися на файли чи каталоги з
*попередніх* томів, а не лише на новий, — розміщені в секції першими, бо
виправлення має передувати будь-якому новому запису, який воно інакше
могло б погасити, §7 `XD`), записи `D` для будь-яких каталогів, які цей том
вводить уперше (наявні каталоги не повторюються), записи `F` цього тому, за
потреби псевдоніми `S` на вже архівований вміст, і закривається відповідним
рядком `VOLUME_END`.

**Важливий наслідок носіїв одноразового запису:** оскільки записаний том не
можна переписати, вбудована в нього копія індексу заморожена на тому стані,
яким бібліотека була на момент запису цього тому. Виправлення, зроблені
пізніше, з'являються лише в копіях індексу, записаних на *наступні* томи (і
в робочій майстер-копії на комп'ютері, що будує архів) — власна копія
старішого тому не покаже пізніші виправлення `AF`/`XF`/`XD`/`RD`/`RF`.
Узгоджуючи стан, віддавайте перевагу копії з найновішого (з найбільшим
номером) доступного тому.

## 9. Розібраний приклад

Розбір [`samples/music.bdea`](samples/music.bdea) за його чотирма томами:

1. **Music-001** записується першим. Він оголошує `Rafael Krux` (`dir_id=1`)
   прямо під коренем бібліотеки, а під ним — папку альбому `Rafael Krux -
   The Epic Baroque Album` (`dir_id=2`) та не пов'язану з нею сусідню папку
   `.info` (`dir_id=3`). У `dir_id=2` потрапляють обкладинка та п'ять
   flac-треків (`file_id` 1–6), причому кожен запис `F` flac-треку несе
   `baroque,epic` у своєму кінцевому полі `extra` (§6, §7 `F`) — конкретна
   ілюстрація того, що `extra` довільне; більше ніщо в прикладі ці теги не
   інтерпретує, вони просто передаються далі. Один з них,
   `F|3|2|...02 Classical Violin Concerto label.flac`, подано з помилкою в
   назві — зайвим словом «label» — виправленою пізніше в `Music-003`
   (пункт 5). Ще один файл у тій самій папці,
   `F|7|2|Vivaldi - Concerto No. 1 in G minor, RV 324.flac`, — не пов'язаний
   з альбомом вміст, який просто теж подано туди; він втрачається в
   `Music-002` (пункт 3). `dir_id=3` (`.info`) містить один невеликий
   немузичний файл, `F|8|3|filedata.txt`; ця папка також повністю зникає в
   `Music-002`. Закриваючи секцію цього тому,
   `VOLUME_END|1|Music-001|2026-08-13_1232|8|82235912|QE4TTLSX56ECJLO3JQMQW74ECQ|3`
   фіксує `8` (`total_vol_files`) і `82235912` (`vol_files_size`) — власну
   кількість записів `F` цього тому та їхній сумарний розмір, прості суми
   по щойно записаних `8` записах `F`, оскільки жодне виправлення ще
   нічого не торкнулося. Його `volume_hash`, `QE4TTLSX56ECJLO3JQMQW74ECQ`,
   конкатенує значення `hash` цих самих `8` записів у порядку появи (без
   роздільника, оскільки всі вони мають однакову фіксовану довжину), а
   потім хешує та кодує цей текст так само, як
   `CONTENT_HASH_ALGORITHM`/`CONTENT_HASH_ENCODING` (§5) вже хешують вміст
   файлів. Жодного архівованого байта при цьому не торкаються — усе
   будується виключно з хешів, що вже лежать в індексі. `last_dir_id`
   дорівнює `3` — найбільшому `dir_id`, призначеному цим томом.
2. **Music-002** записується пізніше. Він оголошує лише те дерево папок,
   яке справді потрібне: `Sandra Bernardo` (`dir_id=4`) та її альбом
   `Tropico Ideal (2018)` (`dir_id=5`), і додає туди п'ять mp3-треків цього
   виконавця (`file_id` 1–5). Крім того, він повторно архівує ще один файл
   прямо під папкою flac-альбому `Music-001` (`dir_id=2`, не
   переоголошується):
   `F|6|2|...03 Baroque Chamber Strings.flac|11707500|54IGSNGTYY4WWM4FKKQMEOLNGW|baroque,epic`
   — чиї `size`+`hash` **ідентичні** файлу
   `F|4|2|...03 Baroque Chamber Strings.flac` з `Music-001`. Це саме той
   конкретний випадок, для виявлення якого існує модель ідентичності
   вмісту формату (§3): той самий вміст, інший том, і жодної причини
   замінювати оригінал — усе одно розпізнається як один і той самий вміст
   через `size`+`hash`. Що саме застосунок обере робити з цим (пропустити
   повторний запис байтів, все одно записати їх заради надлишковості,
   попередити користувача тощо) — це вже політика реалізації, див. §10.
3. На початку секції `Music-002`, одразу після `VOLUME_START`, разом
   записано три виправлення:
   - `AF|1|4|2026-08-14_1111` — з двох тепер відомих копій вмісту «03
     Baroque Chamber Strings» (`F|4|2` з `Music-001` і `F|6|2` з
     `Music-002` з пункту 2 вище, з однаковим `size`+`hash`), це оголошує
     оригінал з `Music-001` (`volume=1, file=4`) канонічним надалі. Копію
     з `Music-002` при цьому не чіпають і не позначають `XF` — вона
     лишається валідною архівною копією, просто більше не тією, що
     показується/вважається канонічною.
   - `XF|1|7|2026-08-14_1111` — не пов'язане виправлення: воно оголошує,
     що файл 7 з `Music-001` (`Vivaldi - Concerto No. 1 in G minor, RV
     324.flac`) став нечитабельним/втраченим на цьому диску. Оскільки
     більше ніщо в бібліотеці не має такого самого хешу, цей трек фактично
     втрачено з архіву, якщо тільки його не відновлять і не додадуть
     повторно пізніше.
   - `XD|3|2026-08-14_1111` — також не пов'язане: воно одразу вилучає з
     активного подання папку `.info` з `Music-001` (`dir_id=3`) та її

4. Закриваючи секцію `Music-002`, рядок
   `VOLUME_END|2|Music-002|2026-08-14_1111|6|41474037|BV6N47NFZD6XHIFB2EH2HR625I|5`
   фіксує `6` для `total_vol_files` і `41474037` для `vol_files_size` —
   власні `6` записів `F` цього тому (`5` нових mp3-треків плюс зайвий
   дублікат flac з пункту 2) та їхній сумарний `size`, пораховані рівно
   так, як їх фізично записано, незалежно від `AF`, яке одразу ж заміщує
   один із них (§7 `VOLUME_END`, §10) — `total_vol_files`/`vol_files_size`
   — це фізичні факти за один том, а не розв'язане активне подання
   бібліотеки. `volume_hash`, `BV6N47NFZD6XHIFB2EH2HR625I`, побудований
   так само, як і в `Music-001`, але лише з `6` хешів `F` цього тому — він
   не продовжує й не поєднується з `volume_hash` тому `Music-001`,
   оскільки `volume_hash` завжди обмежений одним томом, а не є значенням
   для всієї бібліотеки. `last_dir_id` стає `5` — найбільшим `dir_id`,
   призначеним будь-яким із двох томів на цей момент. Читач, якому потрібна
   *активна* кількість файлів/розмір бібліотеки на цей момент, розв'язує
   повний журнал (§10): з `14` записів `F`, записаних на цей момент (`8` з
   `Music-001` плюс `6` з `Music-002`), `F|7|2` з `Music-001` (позначений
   `XF`), `F|8|3` з `Music-001` (вилучений через `XD`) і `F|6|2` з
   `Music-002` (заміщений через `AF`) — неактивні, тож лишається `11`
   активних записів — але жодне поле в жодному `VOLUME_END` не вказує `11`
   прямо.
5. **Music-003** записується ще пізніше й не додає жодного нового
   архівованого вмісту — його секція складається лише з виправлень, нового

     додаючи суфікс «(flac)», заздалегідь, до появи «(mp3)»-сиблінга, який
     ця сама секція введе нижче, тож обидві папки отримають розрізнювані
     назви.
   - `RF|1|3|2|Rafael Krux - The Epic Baroque Album - 02 Classical Violin

   - `D|6|1|Rafael Krux - The Epic Baroque Album (mp3)` вводить нову

   - `F|2|6`, `F|3|6`, `F|4|6` додають mp3-версії трьох flac-треків — інші

   - Закриваючи цей том, рядок

     цього тому нижче: `XD` гасить лише те, що подано під його `dir_id` на

     `dir_id=4`, ні `dir_id=5` не отримують нового запису `D`, оскільки
     їхні пари `(parent_dir_id, dir_name)` вже назавжди належать їм (§7 `D`) —
     `Music-004` взагалі не вводить жодної нової директорії.

## 10. Нотатки для розробників

Це наслідки формату, які варто мати на увазі при розробці застосунку над
ним. Це поради, а не додаткові правила формату — ніщо тут не скасовує
нормативних визначень записів із §7, і розробник вільний використовувати,
адаптувати чи ігнорувати будь-що з цього на власний розсуд.

- **`file_id` локальний для тому, `dir_id` глобальний, імена не є
  ідентичністю.** Ніколи не використовуйте `file_id` окремо як міжтомовий
  ключ — завжди в парі з `volume_id` (`file_key`). `dir_id` такої пари не
  потребує — він сам по собі вже є повною, стабільною ідентичністю, і його
  ніколи не потрібно узгоджувати між томами. Ніколи не використовуйте
  `file_name` для виявлення дублікатів — для ідентичності файлу
  використовуйте `size`+`hash`.
- **Виявлення дублікатів — це пошук `size`+`hash` у межах усієї
  бібліотеки.** Формат дає засіб виявити, що вміст уже існує десь у
  бібліотеці (§3, §9); він свідомо **не** визначає, чи означає запис `F`,
  що байти фізично записані саме на носії цього конкретного тому — цей
  стандарт регламентує лише формат індексного файлу (§1), а не поведінку
  застосунку. Чи записувати байти дубліката повторно (надлишковість), чи
  пропустити фізичний запис (економія місця) — це рішення політики, яке
  ухвалює застосунок; сам формат індексу на це не відповідає. У будь-якому
  разі виявити збіг — механічна дія, а вирішити, що з ним робити — ні:
  показати архіваріусу знайдений збіг `size`+`hash` («усе одно заархівувати
  й назвати канонічним (`AF`), зробити псевдонім без повторного запису
  байтів (`S`, §7 `S`), позначити наявну копію зниклою, якщо вона й справді
  зіпсована (`XF`), чи лишити обидва як незалежні копії?») — це справа
  застосунку, а не щось, що формат вирішує сам (§7).
- **Підрахунок активних файлів при використанні `AF`/`S`.** `AF` (§7
  `AF`) називає рівно один запис канонічним серед набору записів `F` з
  однаковим `size`+`hash`; для підрахунку весь цей набір рахується як
  один активний файл, а не по одному на копію. Псевдонім `S` (§7 `S`)
  ніколи не рахується як окремий файл, оскільки він і не тримав власного
  вмісту. Жоден із двох механізмів не є обов'язковим — два незалежні
  записи `F`, що випадково мають спільний вміст, без жодного `AF` між
  ними, обидва лишаються врахованими як активні. Чи створювати для
  псевдоніма `S` справжній симлінк у файловій системі, і як саме — це
  повністю на розсуд застосунку.
- **Потомні поля `VOLUME_END` не є контрольною точкою для всієї
  бібліотеки.** `total_vol_files`/`vol_files_size`/`volume_hash` описують
  лише те, що фізично додала власна секція певного тому — вони нічого не
  кажуть про те, які з цих записів досі активні після врахування пізніших
  виправлень (див. нижче). Для підтвердження активної кількості файлів чи
  обсягу байтів бібліотеки швидкого шляху немає — розв'язуйте весь
  накопичувальний журнал. А от `last_dir_id` разом із `date_time`
  найновішого `VOLUME_END` самі по собі достатні, щоб визначити, який із
  двох файлів `.bdea`, що претендують описувати ту саму бібліотеку, є
  актуальнішим — наприклад, дві однойменні копії, знайдені на різних
  томах. Оскільки `dir_id` лише зростає і ніколи не використовується
  повторно (§7 `D`), а `date_time` позначає момент формування цієї секції
  (§6 `date_time`), той файл, чий найновіший `VOLUME_END` несе більший
  `last_dir_id` (або пізнішу `date_time`), і є повнішою, актуальнішою
  копією.
- **Розв'язання активного подання.** Наразі активні файли — це записи
  `F`, не покриті пізнішим `XF`, і не подані — прямо чи транзитивно — під
  каталогом, покритим пізнішим `XD`, скориговані з урахуванням будь-якого
  `AF`, що явно їх називає. Показані `dir_id`/`file_name` файлу чи
  псевдоніма — це те, що каже найновіший `RF` для цього `(volume_id,
  file_id)`, або власний запис `F`/`S`, якщо такого `RF` немає; показані
  `parent_dir_id`/`dir_name` каталогу розв'язуються так само, через `RD`.
  Записи й виправлення — це не два окремі проходи: коректний читач
  обробляє весь накопичувальний журнал по порядку, а не лише власні рядки
  `F`/`D` найновішого тому.
- **Розбирайте заголовок один раз на файл, перед будь-якими даними.**
  Декларації `! TYPE`/`! RECORD` слід прочитати перед будь-яким рядком
  даних, оскільки саме вони визначають розкладку полів для цього файлу
  (§4). Це одноразова дія для конкретного `.bdea` файлу, а не дія на
  кожен рядок: розберіть заголовок один раз, закешуйте оголошену ним
  розкладку полів і далі використовуйте цей кеш для кожного наступного
  рядка даних у тому самому файлі. Повторити цей крок читачеві треба лише
  тоді, коли він переходить до **іншого** `.bdea` файлу — наприклад,
  індексу іншої бібліотеки, — оскільки саме заголовок цього іншого файлу,
  а не попереднього, є джерелом правди для його розкладки полів. Не
  зашивайте порядок полів жорстко лише на основі цього документа —
  ставтеся до декларацій усередині кожного файлу як до джерела правди для
  його `VERSION`.

## 11. Версіонування

`! VERSION` у заголовку визначає версію схеми, якій відповідає файл, у
форматі `MAJOR.MINOR` (наприклад, `1.0`, `1.2`, `2.0`) — наразі `1.0`.

**Молодша версія (`MINOR`) — зворотносумісна, адитивна.** Збільшення лише
`MINOR` (наприклад, `1.0` → `1.1`) означає, що будь-який файл із меншою
молодшою версією в межах тієї самої `MAJOR` лишається повністю валідним і
коректно інтерпретованим під новою: жодна вже оголошена сутність не
змінює сенсу, форми чи не стає обов'язковою. Тому читач, що реалізує
`MAJOR.N`, здатен коректно прочитати й будь-який файл із `MAJOR.M`, де
`M <= N`, — підтримка накопичується «згори вниз» у межах однієї старшої
версії. Зміни, які кваліфікуються як молодші:

- Додавання нового необов'язкового кінцевого поля до вже оголошеного
  `! RECORD` — той самий механізм, який уже використовує `extra?` (§7,
  преамбула); читач, що не знає про нове поле, просто його не бачить,
  так само як і з будь-яким іншим необов'язковим кінцевим полем.
- Додавання нової заголовкової декларації (§5), відсутність якої не
  змінює трактування жодного наявного заголовка чи запису — читач, що її
  не розпізнає, може її проігнорувати й далі коректно обробляти все
  інше у файлі.

**Старша версія (`MAJOR`) — з розривом сумісності.** Збільшення `MAJOR`
(наприклад, `1.2` → `2.0`, що скидає `MINOR` до `0`) означає, що файли по
різні боки цієї межі не гарантовано сумісні: від читача, побудованого під
`1.x`, не очікується коректне читання файлу `2.x`, і навпаки. Усе, що не
підпадає під критерії молодшої зміни вище, є старшою зміною, зокрема:

- Зміна сенсу, типу чи позиції вже оголошеного поля в наявному
  `! RECORD`.
- Видалення поля, тега запису чи заголовкової декларації.
- Перетворення наявного необов'язкового поля на обов'язкове, або навпаки.
- Введення нового тега запису чи нового обов'язкового поля, яке читач,
  побудований під попередню версію, не має способу пропустити й далі
  коректно відтворити бібліотеку.

Читач має завжди довіряти саме тому `! VERSION`, який оголошено в
конкретному файлі (§10 «Розбирайте заголовок один раз на файл, перед
будь-якими даними»), а не
припущенням, виведеним лише з цього документа, — цей розділ описує, як
мають поводитися ці два числа, а не замінює їх читання.
