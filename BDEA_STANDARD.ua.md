# Стандарт формату індексу BDEA

**BDEA — Backup Data Extended Archive.** Формат довготривалого офлайн-архіву
для носіїв з високою стабільністю та одноразовим записом (оптичні диски типу
BD-R XL, стрічкові системи LTO тощо). Цей документ описує формат індексного
файлу `.bdea`. Він не визначає поведінку конкретних застосунків (див.
[§10](#10-нотатки-для-розробників-bdea-generator--bdea-browser)).

Це авторитетний опис формату. Канонічний розібраний приклад — у
[`samples/Music.bdea`](samples/Music.bdea).

Це переклад [`BDEA_STANDARD.md`](BDEA_STANDARD.md). У разі розбіжностей
англомовна версія має пріоритет.

## 1. Призначення та межі стандарту

Мета BDEA — дати змогу згодом відновити **бібліотеку** архівованих файлів у
повній логічній структурі, а не просто набір байтів, без залежності від
початкового комп'ютера, бази даних чи спеціального програмного забезпечення.
Стандарт стосується **виключно** формату індексного файлу `.bdea`: як текстом
описати структуру бібліотеки, томи, каталоги, файли та історію їх змін. Він
не регламентує фізичне розташування даних на диску, програмне забезпечення
для запису дисків чи політику резервного копіювання.

## 2. Базові поняття

| Термін | Значення |
|---|---|
| **Archive (архів)** | Загальна структура BDEA: одна або кілька незалежних бібліотек. |
| **Library (бібліотека)** | Логічно ізольована колекція даних (наприклад, `Music`, `Documents`, `Photos`). Має власний простір каталогів, власний індекс `.bdea` і може бути відновлена незалежно від інших бібліотек. |
| **Volume (том)** | Один фізичний носій (один диск), що належить бібліотеці. Бібліотека росте, додаючи томи з часом (`Music-001`, `Music-002`, ...). |

**Бібліотеки повністю ізольовані одна від одної.** Бібліотека ніколи не
посилається на іншу бібліотеку, дублікати між бібліотеками не виявляються, і
кожна бібліотека має власні правила та власний шлях відновлення. BDEA — це
набір автономних структур для кожної бібліотеки, а не єдиний монолітний
архів.

## 3. Модель ідентифікації файлів

Використовуються два окремі, свідомо розділені поняття «ідентичності»:

- **Фізична/позиційна ідентичність** — `(volume_id, file_id)`. Ідентифікує
  один *запис* архівованого файлу всередині бібліотеки: на якому томі його
  записано і його локальний ід в межах цього тому. `file_id` унікальний лише
  в межах свого `volume_id`.
- **Ідентичність вмісту** — `size` + `hash`. Ідентифікує *чим файл насправді
  є*, незалежно від його імені чи розташування. Два записи з однаковими
  `size`+`hash` — це один і той самий вміст, де б він не зустрічався.

Наслідки використання ідентичності вмісту замість імені файлу:

- Дублікати вмісту будь-де в бібліотеці можна виявити (порівнюючи
  `size`+`hash` серед усіх записів `F`, що вже є в індексі).
- Цілісність вмісту можна перевірити за записаним хешем.
- Файл може переміщатися між каталогами, або навіть бути доданим повторно під
  іншим іменем, не втрачаючи своєї ідентичності.

Ім'я ніколи не є авторитетним джерелом — це метадані, а не ідентичність.

## 4. Загальна структура файлу

**Іменування файлів.** Індексний файл бібліотеки називається
`<LIBRARY>.bdea`, де `<LIBRARY>` відповідає значенню заголовка `! LIBRARY`
(наприклад, бібліотека, оголошена як `! LIBRARY Music`, зберігається як
`Music.bdea`). Один файл на одну бібліотеку; саме ім'я файлу вже визначає, до
якої бібліотеки він належить, що дозволяє будувати архів як просту колекцію
файлів `<LIBRARY>.bdea` без будь-якого додаткового «індексу індексів».

Файл `.bdea` — це текст у UTF-8 з двома видами рядків:

- **Декларації** — починаються з `!`, токени розділені пробілами:
  `! KEYWORD value...`. Це машинно-читані рядки.
- **Коментарі** — починаються з `#`, довільний текст, ігнорується парсерами.
- **Записи** — рядки даних формату `TAG|поле1|поле2|...`, розділені `|`.
  `TAG` — це те, що визначено декларацією `! RECORD` (§7) — один або кілька
  символів (`VOLUME_START`, `VOLUME_END`, `D`, `F`, `S`, `A`, `X` у поточній
  схемі).

Порожні рядки допускаються як візуальні розділювачі (наприклад, між секціями
томів).

**Формат є самоописовим.** Порядок полів для кожного тегу запису не
зашитий жорстко в цьому стандарті — він оголошується прямо у файлі через
рядки `! RECORD` (§7), які мають з'явитися перед будь-яким рядком даних із
цим тегом. Коректний парсер спочатку читає декларації `! TYPE`/`! RECORD`, а
потім використовує це відображення для розбору наступних рядків даних.

**Індекс є доповнюваним (append-only) і накопичувальним.** Той самий файл
`.bdea` *доповнюється* щоразу, коли виробляється новий том, і оновлений файл
записується також і на цей новий том. Це означає:

- Копія індексу на кожному томі містить *усю історію бібліотеки до цього
  моменту* — а не лише вміст цього конкретного тому.
- Найновіший том, який у вас є, завжди містить найповніший/найактуальніший
  індекс усієї бібліотеки (наслідки цього для носіїв одноразового запису —
  див. §8).
- В принципі бібліотеку можна повністю переглянути з копії індексу лише
  одного диска, навіть без наявності решти фізичних дисків — ця копія
  вкаже, на якому томі фізично лежать байти будь-якого конкретного файлу.

## 5. Заголовкові декларації

З'являються один раз, на початку файлу, перед будь-якою секцією тому.

| Декларація | Приклад | Значення |
|---|---|---|
| `! TEXT_ENCODING` | `utf-8` | Кодування самого файлу `.bdea`. |
| `! TEXT_NORMALIZATION` | `NFC` | Форма нормалізації Unicode для тексту файлу. |
| `! ARCHIVE_TYPE` | `BDEA` | Ідентифікатор формату. |
| `! VERSION` | `1` | Версія формату (див. §11). |
| `! LIBRARY` | `Music` | Назва цієї бібліотеки. |
| `! NAME_ENCODING` | `utf-8` | Кодування, що використовується для полів `name` файлів/каталогів. |
| `! NAME_NORMALIZATION` | `NFC` | Нормалізація Unicode, застосована до імен. |
| `! NAME_FORBIDDEN_CHARACTERS` | `/ \ : * ? " < > \|` | Символи, яких не повинно бути в іменах (надмножина зарезервованих символів Windows/exFAT — безпечний вибір для носія, який мають читати з будь-якої файлової системи). |
| `! CONTENT_HASH_ALGORITHM` | `md5` | Алгоритм хешування, що ідентифікує вміст файлу. |
| `! CONTENT_HASH_ENCODING` | `base32` | Кодування, у якому хеш подано текстом. |
| `! CONTENT_HASH_SCOPE` | `file-content` | Що саме хешується (сирі байти файлу, а не, наприклад, ім'я+вміст). |

Це канонічна, чинна форма заголовка, і саме її мають випромінювати нові
файли `.bdea`.

## 6. Система типів (`! TYPE`)

Оголошує примітивний тип кожного поля, що використовується в записах, аби
файл був самоописовим і придатним для незалежного розбору.

| Назва типу | Вид | Примітки |
|---|---|---|
| `dir_id` | `uint32` | Глобальний для всієї бібліотеки — призначається один раз на каталог і ніколи не використовується повторно, незалежно від того, який том його ввів. Реальні значення починаються з `1`; `0` зарезервовано для позначення неявного кореня бібліотеки (§7 `D`, `F`, `S`). |
| `last_dir_id` | `uint32` | Той самий вид, що й `dir_id`; найбільший `dir_id`, призначений у бібліотеці станом на цей том (§7 `VOLUME_END`). |
| `parent_dir_id` | `uint32` | `0` = корінь простору імен бібліотеки. |
| `file_id` | `uint64` | Локальний для тому. |
| `target_file_id` | `uint64` | Той самий вид, що й `file_id`; запис `F`, на який посилається псевдонім `S` (§7 `S`). |
| `size` | `uint64` | Байти. |
| `name` | `string max=120` | Ім'я файлу чи каталогу. |
| `hash` | `string max=32` | Закодований хеш вмісту (26 символів для base32 MD5; додатковий запас довжини дозволяє довший хеш, якщо `CONTENT_HASH_ALGORITHM` колись зміниться). |
| `extra` | `string max=256` | Довільне поле в записах `D`/`F` (§7 `D`, §7 `F`), наприклад для тегів. Залишається порожнім, якщо застосунок його не використовує. |
| `volume_id` | `uint32` | Локальний для бібліотеки. |
| `target_volume_id` | `uint32` | Той самий вид, що й `volume_id`; том запису `F`, на який посилається псевдонім `S` (§7 `S`). |
| `volume_label` | `string max=120` | Людська/фізична позначка, надрукована на носії. |
| `datetime` | `string max=15` | `YYYY-MM-DD_hhmm` — завжди час, коли *застосунок-виробник* згенерував записи індексу навколо, а не власний час запису фізичного носія (поза межами стандарту, §1). Формування індексних записів одного тому вважається єдиним швидким кроком, тож кожне поле `datetime` у межах секції цього тому (`VOLUME_START`, `VOLUME_END`, будь-які `A`/`X`) традиційно несе *те саме* значення — це не пара «початок/кінець» тривалості фізичного запису. |
| `count` | `uint64` | Загальний невід'ємний вид лічильника, спільний для `files_added`, `files_changed`, `files_deleted`, `total_files` і `total_size` нижче (§7 `VOLUME_END`) — кожен оголошено як власний `! TYPE`, щоб тип поля можна було знайти лише за іменем. |
| `files_added` | `uint64` | Той самий вид, що й `count`; кількість записів `F`, записаних у секції тому (§7 `VOLUME_END`). |
| `files_changed` | `uint64` | Той самий вид, що й `count`; кількість записів `A`, записаних у секції тому (§7 `VOLUME_END`). |
| `files_deleted` | `uint64` | Той самий вид, що й `count`; кількість записів `X`, записаних у секції тому (§7 `VOLUME_END`). |
| `total_files` | `uint64` | Той самий вид, що й `count`; кумулятивна кількість активних файлів у бібліотеці станом на цей том (§7 `VOLUME_END`). |
| `total_size` | `uint64` | Той самий вид, що й `count`; кумулятивний розмір активних файлів у бібліотеці станом на цей том (§7 `VOLUME_END`). |
| `file_key` | `volume_id file_id` | Композитний тип: повна фізична ідентичність запису файлу (§3). |

`file_key` — це композитний тип на рівні документації: він називає поняття
«кортеж, що однозначно локалізує цей запис»; декларації `! RECORD` для
`A`/`X` усе одно перелічують `volume_id`/`file_id` як окремі поля, а не
посилаються на цю композитну назву напряму. У каталогів немає аналогічного
композитного типу: `dir_id` сам по собі вже є повною ідентичністю каталогу,
оскільки він глобальний для всієї бібліотеки.

## 7. Схема записів (`! RECORD`)

Ім'я поля, що закінчується на `?` у декларації `! RECORD`, позначає його як
**необов'язкове й кінцеве**: рядок даних із цим тегом може його не містити —
матиме на одне поле, розділене `|`, менше, ніж оголошено. Станом на
`! VERSION 1` це стосується лише `extra?` у `D` та `F` (нижче) — усі інші
поля обов'язкові. Коректний парсер має приймати рядок `D`/`F` як із кінцевим
полем `extra`, так і без нього, трактуючи відсутнє поле як
порожнє/відсутнє. Саме це дозволяє додати `extra` до рядка пізніше
(наприклад, щоб прикріпити теги), не роблячи невалідними старіші рядки, що
існували до цього поля, і без потреби переписувати кожен наявний рядок.

### `VOLUME_START` / `VOLUME_END` — межа тому

```
! RECORD VOLUME_START volume_id volume_label datetime
! RECORD VOLUME_END volume_id volume_label datetime files_added files_changed files_deleted total_files total_size last_dir_id
```

`VOLUME_START` оголошує один том (один фізичний диск) і відкриває його
секцію; `VOLUME_END` закриває її. Кожен запис `D`, `F`, `S`, `A` та `X` між
`VOLUME_START` і відповідним йому `VOLUME_END` було записано під час
виробництва саме цього тому:

- Записи `D` у цьому діапазоні оголошують каталоги, які цей том вводить
  вперше (§7 `D`) — каталог, що вже існує, не повторюється.
- Записи `F` у цьому діапазоні отримують свій `volume_id` саме з цієї секції
  (§7 `F`) — це єдине місце, де фіксується том файлу.
- Записи `S` у цьому діапазоні отримують свій `volume_id` так само, як і
  `F` (§7 `S`) — хоча *вміст*, на який вони посилаються, може бути на
  будь-якому томі, через власне явне поле `target_volume_id`.
- Записи `A`/`X` можуть з'являтися тут, хоча вони можуть посилатися на файл
  на **будь-якому** томі (§7 `A`, `X`) — для них важливе саме їхнє явне
  поле `volume_id`, а не позиція у файлі.

Поля, спільні для обох записів:

- `volume_id` — внутрішній числовий ід тому в межах бібліотеки; повторюється
  в `VOLUME_END`, аби читач (або людина, що переглядає файл) міг
  переконатися, яку саме секцію закрито, і аби можна було виявити обірвану
  чи пошкоджену секцію (`VOLUME_START` без відповідного `VOLUME_END`).
- `volume_label` — позначка, написана/надрукована на фізичному носії;
  повторюється в `VOLUME_END` з тієї самої причини, що й `volume_id` —
  якщо значення на двох кінцях секції розійдуться, це ознака проблеми.
- `datetime` — коли застосунок-виробник згенерував індексні записи цього
  тому (§6 `datetime`). Формування секції одного тому вважається єдиним
  швидким кроком — окремим від фізичного запису і зазвичай значно
  коротшим за нього — тож це значення однакове на `VOLUME_START`,
  `VOLUME_END` і будь-яких записах `A`/`X` у тій самій секції; це не пара
  «початок/кінець» тривалості фізичного запису.

Поля, властиві лише `VOLUME_END` — підсумок власних змін цього тому плюс
контрольна точка стану всієї бібліотеки станом на цей том (навіщо вони
потрібні і як застосунок може ними скористатися — див. §10):

- `files_added` — кількість записів `F`, записаних у секції цього тому.
- `files_changed` — кількість записів `A`, записаних у секції цього тому
  (вони можуть виправляти файли на будь-якому томі, не лише на цьому — §7
  `A`).
- `files_deleted` — кількість записів `X`, записаних у секції цього тому,
  незалежно від того, видаляють вони `F` чи `S` (§7 `X`) — так само можуть
  посилатися на будь-який том.
- `total_files` — накопичувальна кількість файлів, активних у бібліотеці
  станом на цей том, тобто розмір повністю реконструйованого активного
  подання (§10) — **не** сирий наростаючий підсумок усіх коли-небудь
  записаних `F`. Заміщені чи видалені записи розв'язуються так само, як їх
  розв'язує повна реконструкція, тож це значення не можна підтримувати
  простим приростом за томом (§10). Записи `S` (§7 `S`) сюди ніколи не
  враховуються — псевдонім додає нове ім'я, а не новий вміст; він уже
  врахований через свою ціль.
- `total_size` — сума `size` по тому самому активному набору; так само не
  залежить від того, скільки існує псевдонімів `S`.
- `last_dir_id` — найбільший `dir_id`, призначений у бібліотеці станом на
  цей том; на відміну від `total_files`/`total_size`, це просто монотонний
  максимум, не залежний від `A`/`X` (§7 `D`).

Самі додавання `S` не враховуються жодним із трьох лічильників вище — для
псевдонімів немає окремого лічильника за томом станом на `! VERSION 1`;
лише їх видалення (через `X`) потрапляє до `files_deleted`.

```
VOLUME_START|1|Music-001|2026-08-13_1232
...
VOLUME_END|1|Music-001|2026-08-13_1232|9|0|0|9|70477923|4
```

### `D` — каталог

```
! RECORD D dir_id parent_dir_id name extra?
```

Логічний каталог у дереві простору імен бібліотеки.

- `dir_id` — глобальний для всієї бібліотеки: призначається один раз, коли
  том вперше вводить цей каталог, і ніколи не переприсвоюється пізнішим
  томом — навіть тим, що додає до нього ще файли. Призначені значення
  починаються з `1`; корінь бібліотеки неявний і ніколи не отримує
  власного запису `D` — `0` зарезервовано, щоб позначати «корінь» будь-де,
  де на нього посилається поле виду `dir_id` (`parent_dir_id` нижче, а
  також власне поле `dir_id` у `F`/`S`, §7 `F`, §7 `S`).
- `parent_dir_id` — `dir_id` батьківського каталогу (`0` = корінь). Оскільки
  `dir_id` глобальний, батьківський каталог міг бути оголошений і раніше,
  не обов'язково поточним томом.
- `name` — ім'я каталогу.
- `extra` — необов'язкове, кінцеве поле (преамбула §7); довільне (§6
  `extra`), наприклад для тегів. Порожнє або відсутнє, якщо застосунок його
  не заповнює.

Каталоги формують єдине, стабільне, доповнюване (append-only) дерево
простору імен для всієї бібліотеки (а не по одному дереву на том). Порожні
каталоги можна не вказувати. Оскільки `dir_id` глобальний, конкретна
логічна папка (наприклад, `Music/Rafael Krux`) оголошується рівно один раз
— тим томом, що вводить її вперше; пізніший том, що додає файли до вже
наявної папки, не переоголошує її, а просто посилається на вже наявний
`dir_id` у своїх записах `F` (див. розібраний приклад, §9).

```
D|1|0|Music
D|2|1|Rafael Krux
```

### `F` — файл

```
! RECORD F file_id dir_id name size hash extra?
```

Запис архівованого файлу. **`volume_id` не є полем `F`.** Том файлу —
позиційний, а не поле самого запису: запис `F` належить тому тому, у секції
`VOLUME_START`...`VOLUME_END` якого він фізично знаходиться (§7
`VOLUME_START`/`VOLUME_END`) — читач відстежує «поточний том» під час
послідовного сканування і проставляє його кожному зустріченому рядку `F`.

Це свідомий вибір заради економії місця: реальні бібліотеки міститимуть
значно більше файлів, ніж томів, тож повторювати `volume_id` в кожному
записі `F` було б марнотратно, тоді як відстежувати його один раз на секцію
для читача нічого не коштує. Каталог файлу, натомість, не позиційний:
`dir_id` — глобальний для всієї бібліотеки (§7 `D`), тож читач розв'язує
його відносно єдиного, спільного для всієї бібліотеки дерева каталогів,
побудованого з усіх побачених досі записів `D`, незалежно від того, який
том оголосив цей каталог.

- `file_id` — унікальний лише в межах `volume_id` (повна фізична
  ідентичність — `(volume_id, file_id)`, тобто `file_key`); сам `volume_id`
  береться з секції тому, що охоплює цей запис, а не з самого запису.
- `dir_id` — глобальний ід каталогу, що містить файл (§7 `D`); `0` означає,
  що файл лежить прямо в корені бібліотеки — той самий сентінел, що й у
  `parent_dir_id` (§7 `D`) — корінь не має власного запису `D`, на який
  можна було би послатися.
- `name` — ім'я файлу (не ідентичність, див. §3).
- `size`, `hash` — ідентичність вмісту (§3); використовуються для виявлення
  дублікатів, що вже є будь-де в бібліотеці, та для перевірки цілісності.
- `extra` — необов'язкове, кінцеве поле (преамбула §7); довільне (§6
  `extra`), наприклад для тегів. Порожнє або відсутнє, якщо застосунок його
  не заповнює.

```
F|1|3|cover.jpg|125142|P625I35ZX7YR6Y4NILBDDE3MQP
F|2|3|...02 Classical Violin Concerto.flac|8541907|VUMGOS3L25V5JEP4LU6OI5PXQG|baroque,epic
```

### `S` — симлінк

```
! RECORD S file_id dir_id name target_volume_id target_file_id
```

Псевдонім: нова позиція в дереві, яка сягає вмісту, що вже тримає десь
інший запис `F`, замість архівування ще однієї фізичної копії. Типове
застосування: архіваріус свідомо хоче, щоб той самий вміст був доступний
більш ніж з одного місця в бібліотеці (наприклад, той самий `cover.jpg` у
двох різних папках альбомів), без повторного запису цих байтів на том.

- `file_id` — власний локальний ід цього псевдоніма, узятий з *того самого*
  лічильника за томом, що й `file_id` у `F`, а не з окремого простору
  нумерації — тож `(volume_id, file_id)`, де `volume_id` визначається
  позиційно так само, як у `F` (§7 `VOLUME_START`/`VOLUME_END`), однаково
  адресує і `F`, і `S`. Саме це дозволяє `X` видаляти псевдонім так само,
  як він видаляє файл (§7 `X`).
- `dir_id` — де саме в дереві бібліотеки живе цей псевдонім (глобальний,
  точно як `dir_id` у `F`, включно з `0` як позначенням кореня, §7 `D`, §7
  `F`). На відміну від `A`/`X`, `S` створює цілком нову позицію в дереві,
  тож — на відміну від `A`/`X` — йому це поле потрібне.
- `name` — власне ім'я цього псевдоніма в цій позиції.
- `target_volume_id`, `target_file_id` — наявний запис `F`, чийого вмісту
  сягає цей псевдонім (може бути на будь-якому томі, той самий шаблон, що
  й у `A`/`X`, §3 `file_key`).

`S` не несе власних `size`/`hash` — вміст, якого він сягає, вже врахований
через `F`-запис своєї цілі, тож псевдонім додає дереву нове ім'я, не
додаючи нових байтів чи нового врахованого вмісту (§7 `VOLUME_END`, §10).

**Розв'язання цілі через `A`/`X`.** Поле цілі псевдоніма визначає *який
саме вміст* він сягає, а не назавжди зафіксований фізичний запис: читач
розв'язує його так само, як будь-який інший вміст у бібліотеці — через
історію `A`/`X`, застосовну до цього вмісту (§10 «Читайте `A`/`X` перш ніж
довіряти `F`»). Конкретно: якщо цільовий запис пізніше заміщено через `A`
(архіваріус перейменував/переніс цей файл — див. нижче), псевдонім
прозоро переходить на новий канонічний запис; якщо цільовий запис пізніше
позначено `X`, і ніде в бібліотеці не лишилось іншої копії цього вмісту,
псевдонім стає «висячим» — так само, якби вміст просто зник.

**`S` — це не спосіб перейменувати чи перенести файл.** Якщо тому самому
*файлу* (а не свідомо другій копії) потрібне інше ім'я чи каталог надалі
— це завдання для `A`: записати новий `F`-запис за новим іменем/місцем
(що посилається на той самий вміст) і оголосити його канонічним через `A`
(§7 `A`, §9). `S` існує лише для випадку, коли архіваріус хоче, щоб той
самий вміст був доступний із додаткового місця *без* повторного запису —
і ніколи як заміна `A`. Формат не може механічно відрізнити ці два наміри
— обидва починаються з «той самий вміст, нове ім'я» — тож який із них
правильний, залежить від того, що архіваріус насправді мав на увазі, а не
від того, що може перевірити парсер.

```
S|18|4|cover.jpg|1|1
```

(Із секції `Music-001` у `samples/Music.bdea` — цей псевдонім сягає
`F|1|3|cover.jpg` із другої позиції в дереві, `dir_id=4`, обкладинки в
mp3-папці, замість повторного архівування цих байтів; див. §9.)

### `A` — активний

```
! RECORD A volume_id file_id datetime
```

Оголошує, що `(volume_id, file_id)` — канонічний/пріоритетний фізичний запис,
який слід використовувати для цього вмісту надалі. На відміну від `D`/`F`/`S`,
`A` може вказувати на файл на **будь-якому** томі (не лише на поточному).
Типове застосування: той самий вміст архівується більше одного разу —
можливо, на кількох різних томах (збіг `size`+`hash`, наприклад той самий
файл, доданий пізніше під іншим іменем/розташуванням, див. §9) — `A` називає
рівно один із цих записів «тим самим» файлом для показу/використання надалі.
Це **не** вимагає позначати решту заміщених записів як `X` — вони можуть
лишатися цілком валідними, читабельними архівними копіями; просто більше не
є тими, на які вказують як на канонічні. Скільки б копій цього вмісту не
існувало по всьому архіву, після того як `A` назве одну з них, у активному
підрахунку `total_files`/`total_size` (§7 `VOLUME_END`) лишається рахуватися
рівно одна — решта випадають з підрахунку без потреби в `X`.

- `volume_id`, `file_id` — запис, який оголошується канонічним (§3
  `file_key`). Завжди запис `F`, ніколи `S` (§7 `S`) — псевдонім не
  тримає власного вмісту, тож ніколи не може бути *тією* канонічною
  фізичною копією чогось; «канонічний для вмісту» має сенс лише серед
  записів, що справді тримають байти.
- `datetime` — коли це виправлення було дописано до індексу (§6
  `datetime`) — не властивість жодної з фізичних копій; збігається з
  позначкою часу `VOLUME_START`/`VOLUME_END` тому, до якого належить.

```
A|2|6|2026-08-14_1111
```

### `X` — видалений

```
! RECORD X volume_id file_id datetime
```

Оголошує, що запис за адресою `(volume_id, file_id)` слід пропускати при
подальшому відновленні бібліотеки. Як і `A`, може посилатися на запис
будь-якого тому. Що саме означає «зниклий», залежить від типу запису:

- Для запису `F`: фізична копія стала недоступною — нечитабельною,
  пошкодженою чи втраченою саме на цьому носії. Якщо десь у бібліотеці
  немає іншого, неушкодженого запису `F` з таким самим `size`+`hash`, цей
  вміст фактично втрачено.
- Для запису `S` (§7 `S`): видалено сам псевдонім — з вмістом, на який він
  посилався, нічого не сталося, він просто перестає бути досяжним із цієї
  однієї позиції в дереві.

- `volume_id`, `file_id` — запис, який позначають як зниклий (§3
  `file_key`).
- `datetime` — коли це виправлення було дописано до індексу (§6
  `datetime`) — не момент, коли носій справді вийшов з ладу чи коли це
  було помічено; збігається з позначкою часу `VOLUME_START`/`VOLUME_END`
  тому, до якого належить.

```
X|1|6|2026-08-14_1111
```

`A` та `X` — незалежні механізми: конкретне виправлення може
використовувати один із них, інший, або обидва, але жоден не мається на
увазі автоматично при наявності іншого. Разом вони — те, як BDEA підтримує
виправлення без перезапису носіїв одноразового запису: старий запис
лишається фізично на місці; `A` може перенаправити, яка копія вважається
канонічною, а `X` може позначити конкретну копію як таку, що зникла.

`A` та `X` — обидва ручні виправлення, які видає архіваріус; ніщо у форматі
не пише їх автоматично на основі збігу `size`+`hash`. Типовий тригер —
архіваріус переглядає збіги вмісту, які виявив BDEA-Generator (§10), і вирішує
окремо для кожного випадку: перейменувати/перенести файл надалі (записати
`A`), додати псевдонім замість повторного запису байтів, якщо той самий
вміст свідомо має бути в кількох місцях (записати `S`, §7 `S`),
зафіксувати, що копія зіпсувалася (записати `X`), або просто лишити два
незалежні файли, що мають спільний вміст, як є.

## 8. Секції томів і зростання з часом

Тіло файлу — це послідовність секцій томів у порядку їх вироблення:

```
# ----------------- Music-001 -----------------

VOLUME_START|1|Music-001|2026-08-13_1232

D|1|0|Music
...
F|1|3|cover.jpg|125142|...
...
S|18|4|cover.jpg|1|1

VOLUME_END|1|Music-001|2026-08-13_1232|9|0|0|9|70477923|4

# ----------------- Music-002 -----------------

VOLUME_START|2|Music-002|2026-08-14_1111

D|5|1|Sandra Bernardo
...
F|1|6|...

A|2|6|2026-08-14_1111
X|1|6|2026-08-14_1111

VOLUME_END|2|Music-002|2026-08-14_1111|6|1|1|13|83620060|6
```

Кожен новий том дописує: один рядок `VOLUME_START`, записи `D` для будь-яких
каталогів, які цей том вводить уперше (наявні каталоги не повторюються),
записи `F` цього тому, за потреби псевдоніми `S` на вже архівований вміст,
за потреби виправлення `A`/`X` (які можуть посилатися на файли з
*попередніх* томів, а не лише на новий), і закривається відповідним рядком
`VOLUME_END`.

**Важливий наслідок носіїв одноразового запису:** оскільки записаний диск не
можна переписати, вбудована в нього копія індексу заморожена на тому стані,
яким бібліотека була на момент запису. Виправлення, зроблені пізніше,
з'являються лише в копіях індексу, записаних на *наступні* томи (і в робочій
майстер-копії на комп'ютері, що будує архів) — копія на старішому диску не
покаже пізніші виправлення `A`/`X`. Узгоджуючи стан, віддавайте перевагу
копії з найновішого (з найбільшим номером) доступного тому.

## 9. Розібраний приклад

Розбір [`samples/Music.bdea`](samples/Music.bdea):

1. **Music-001** записується першим. Він оголошує каталоги для
   `Music/Rafael Krux/...(flac)` і `.../...(mp3)`, а також файли обкладинки
   та кількох flac/mp3-треків. Кожен запис `F` flac-треку несе `baroque,epic`
   у своєму кінцевому полі `extra` (§6, §7 `F`) — конкретна ілюстрація того,
   що `extra` довільне; більше ніщо в прикладі ці теги не інтерпретує, вони
   просто передаються далі. Обкладинка в mp3-папці — не друга фізична
   копія: `S|18|4|cover.jpg|1|1` сягає `F|1|3|cover.jpg` з flac-папки,
   замість повторного запису цих байтів (§7 `S`) — це саме той випадок
   свідомого дублювання, для якого існує `S`, на відміну від пункту 2
   нижче, який є помилкою, виправленою через `A`. Закриваючи цю секцію
   тому, `VOLUME_END|1|Music-001|2026-08-13_1232|9|0|0|9|70477923|4`
   рахує `9` файлів, а не `10` — псевдонім не додається до підрахунку
   (§7 `VOLUME_END`).
2. **Music-002** записується пізніше. Він оголошує лише те дерево папок, яке
   справді є новим (`Music/Sandra Bernardo/...`, `dir_id` 5 і 6), і додає
   туди файли нового виконавця. Також він додає ще один файл прямо до
   `Music/Rafael Krux/Rafael Krux - The Epic Baroque Album (flac)` —
   каталогу, який `Music-001` уже оголосив як `dir_id=3` — без повторного
   оголошення:
   (`F|6|3|...02 Classical Violin Concerto number 3.flac|8541907|VUMGOS3L25V5JEP4LU6OI5PXQG|baroque,epic`)
   — чиї `size`+`hash` **ідентичні** файлу `F|3|3|...02 Classical Violin
   Concerto.flac` з `Music-001`. Це конкретний випадок, для виявлення якого й
   існує модель ідентичності вмісту формату (§3): той самий вміст, інший
   том, інша (помилкова) назва — і все одно розпізнається як один і той
   самий вміст через `size`+`hash`. Що саме застосунок робитиме з цим
   (пропустить повторний запис байтів, все одно запише їх заради надлишкової
   копії, попередить користувача тощо) — це вже політика реалізації, див.
   §10.
3. У кінці секції `Music-002` разом записано два *не пов'язані між собою*
   виправлення:
   - `A|2|6|2026-08-14_1111` — з двох тепер відомих копій вмісту «Classical
     Violin Concerto» (`F|3|3` з `Music-001` і `F|6|3` з `Music-002` з
     пункту 2 вище, з однаковими `size`+`hash`) це оголошує копію з
     `Music-002` (`volume=2, file=6`) канонічною для подальшого
     використання. Копію з `Music-001` при цьому не чіпають і не позначають
     `X` — вона лишається валідною архівною копією, просто більше не тією,
     що показується/вважається канонічною.
   - `X|1|6|2026-08-14_1111` — цілком окреме виправлення: воно оголошує, що
     файл 6 з `Music-001` (`05 Vivaldi Like Violin Solo.flac`) став
     нечитабельним/втраченим на цьому диску. Оскільки більше ніщо в
     бібліотеці не має такого самого хешу, цей трек фактично втрачено з
     архіву, якщо тільки його не відновлять і не додадуть повторно пізніше.
4. Закриваючи секцію `Music-002`, рядок
   `VOLUME_END|2|Music-002|2026-08-14_1111|6|1|1|13|83620060|6` фіксує
   власний підсумок цього тому (`6` доданих файлів, `1` зміна, `1`
   видалення) поряд із контрольною точкою стану *всієї* бібліотеки.
   `total_files` дорівнює `13`, а не `15` записам `F`, які обидва томи
   разом записали (`S` із пункту 1 і так ніколи не входив до цих `15`) —
   з цього числа вже виключено `F|3|3` з `Music-001` (замінений через `A`
   вище) та `F|6|3` з `Music-001` (втрачений через `X` вище):
   `15 - 1 - 1 = 13`. `total_size` (`83620060`) — це сума `size` по тому
   самому активному набору з 13 записів, а `last_dir_id` (`6`) —
   найбільший `dir_id`, призначений будь-яким із томів. Читач, що повністю
   реконструює бібліотеку з нуля, має отримати ці самі три числа — якщо ні,
   помилка є або в реконструкції, або в самому індексі (§10).

## 10. Нотатки для розробників (BDEA-Generator / BDEA-Browser)

Це наслідки формату, які варто мати на увазі при розробці застосунків над
ним — а не додаткові правила самого формату:

- **`file_id` локальний для тому, `dir_id` глобальний, імена не є
  ідентичністю.** Ніколи не використовуйте `file_id` окремо як міжтомовий
  ключ — завжди в парі з `volume_id` (`file_key`). `dir_id` такої пари не
  потребує — він сам по собі вже є повною, стабільною ідентичністю, і його
  ніколи не потрібно узгоджувати між томами. Ніколи не використовуйте
  `name` для виявлення дублікатів — для ідентичності файлу використовуйте
  `size`+`hash`.
- **Виявлення дублікатів — це пошук `size`+`hash` у межах усієї
  бібліотеки.** Формат дає засіб виявити, що вміст уже існує десь у
  бібліотеці (§3, §9). Він свідомо **не** визначає, чи означає запис `F`,
  що байти фізично записані саме на диску цього конкретного тому — цей
  стандарт регламентує лише формат індексного файлу (§1), а не поведінку
  застосунку. Чи записуватиме BDEA-Generator байти повторно
  (надлишковість) чи пропустить фізичний запис при виявленні дубліката
  (економія місця) — це рішення політики, яке потрібно ухвалити явно під час
  проєктування BDEA-Generator — сам формат індексу на це не відповідає.
  - Якщо політикою фізичного запису обрати «пропускати при дублікаті»,
    BDEA-Generator/BDEA-Browser знадобиться домовленість про те, *який саме*
    том гарантовано містить фізичні байти для даного хешу (наприклад,
    «найраніший том, де цей хеш з'явився вперше») — такої домовленості поки
    що не існує, і її слід узгодити до того, як BDEA-Generator почне на неї
    покладатися.
  - У будь-якому разі виявити збіг — механічна дія, а вирішити, що з ним
    робити — ні. Завдання BDEA-Generator — показати архіваріусу знайдений
    збіг `size`+`hash`: «схоже на дублікат уже наявного файлу: перейменувати
    чи перенести його (`A`), зробити псевдонім без повторного запису байтів
    (`S`, §7 `S`), чи лишити обидва як незалежні копії?» — а не самому
    вирішувати й писати `A`/`S`/`X` (§7).
- **Заміщений через `A` дублікат не рахується окремим активним файлом, а
  псевдонім `S` не рахується взагалі.** Щойно `A` називає один запис
  канонічним серед набору дублікатів з однаковим вмістом — байдуже,
  скільки томів містять копію — саме він рахується в
  `total_files`/`total_size`; кожен інший запис з тим самим вмістом
  випадає з активного підрахунку, хоч і лишається фізично валідним та
  читабельним (§7 `A`). Розібраний приклад у §9 саме так і робить: `F|3|3`
  з `Music-001` виключається, щойно `F|6|3` з `Music-002` оголошено
  канонічним через `A`. `S` вирішує це питання ще пряміше — обкладинка в
  mp3-папці `Music-001` (§9, пункт 1) ніколи й не була другим записом `F`,
  тож вона й не входила до підрахунку від самого початку. Жоден із двох
  механізмів не є обов'язковим: формат не вимагає, аби кожен збіг
  `size`+`hash` обов'язково отримував `A` чи ставав `S`. Якщо архіваріус
  колись лишить два незалежні записи `F` з однаковим вмістом невиправленими
  — без `A`, без `S` — обидва лишаються врахованими; чи то свідомо, чи
  просто непереглянуто, вирішувати саме це й покликані `A`/`S` (див. вище),
  а механіці важливо лише, чи щось із них написано, а не чому не написано.
  Чи буде *кожен* виявлений дублікат переглянутий і якось вирішений — це вже
  питання робочого процесу BDEA-Generator/архіваріуса, пов'язане з рішенням
  про фізичну дедублікацію вище — але щойно `A` чи `S` написано, саме
  правило підрахунку вже не є вибором.
- **Підсумкові поля `VOLUME_END` водночас слугують контрольною точкою для
  відновлення бази.** Застосунок, що веде постійну базу даних, яка
  дзеркалить бібліотеку, замість повторного розбору всього файлу `.bdea`
  щоразу може зазвичай просто дописати секцію найновішого тому до цієї
  бази, а не переобробляти всю історію з нуля. Перед таким дописуванням
  варто звірити власні поточні `(total_files, total_size, last_dir_id)`
  бази з тими, що записані в *останньому* вже застосованому `VOLUME_END`.
  Якщо вони збігаються — можна безпечно дописати лише нову секцію; якщо ні
  — база розійшлася з індексом (її редагували поза застосунком, вона
  пошкоджена, або це просто інша копія, ніж очікувалося) і потрібна повна
  пересинхронізація — відбудувати базу з індексу, відбудувати індекс з
  бази, або знайти, яка саме копія `.bdea` насправді найновіша (§8).
- **Читайте `A`/`X` перш ніж довіряти `F`.** Набір «наразі активних» файлів
  бібліотеки — це записи `F`, **не** покриті пізнішим `X`, скориговані з
  урахуванням будь-якого `A`, що явно їх називає. Коректний читач обробляє
  весь накопичувальний журнал по порядку, а не лише власні рядки `F`
  найновішого тому.
- **Завжди спершу розбирайте заголовок.** Декларації `! TYPE`/`! RECORD` слід
  прочитати перед будь-яким рядком даних, оскільки саме вони визначають
  розкладку полів для цього файлу (§4). Не зашивайте порядок полів жорстко
  лише на основі цього документа — ставтеся до декларацій усередині
  конкретного файлу як до джерела правди для його `VERSION`.

## 11. Версіонування

`! VERSION` у заголовку визначає версію схеми, якій відповідає файл (наразі
`1`, як визначено вище). Майбутні зміни форми `! TYPE`/`! RECORD` мають
збільшувати цю версію, аби читачі могли виявити несумісну розкладку.
